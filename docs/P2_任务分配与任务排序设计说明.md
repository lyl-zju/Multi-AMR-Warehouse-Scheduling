# P2 任务分配与任务排序设计说明

> 本文档是 P2 算法设计说明。项目题干、分层要求、速度、电量、充电和评价函数的最终规定，以 [项目命题规定.md](./项目命题规定.md) 为准。

## 1. P2 的定位

在当前项目代码分工中，P2 不负责重新构造仓库路网，也不负责生成候选路径。P1 已经给出了关键节点之间的候选路径、路径时间和路径成本，P2 的核心任务是在这些已知信息基础上，决定：

1. 每个任务由哪台 AMR 执行；
2. 每台 AMR 内部的任务执行顺序；
3. 每个任务对应的空驶衔接路径、载货路径，以及粗略开始/完成时间。

P2 的结果会交给 P3。P3 再进一步把路径展开为带时间戳的二维轨迹，检测或修复 AMR 之间的轨迹 footprint 冲突。因此，当前项目中更合理的边界是：

```text
P2：生成尽量好的任务分配与任务顺序
P3：基于 P2 结果进行时间表展开、轨迹展开、冲突检测与消解
```

P2 必须考虑时间窗、衔接路径、AMR 速度、电量阈值、负载均衡和粗略延期。基础层 P2 需要检查任务序列的耗电和剩余电量，但不插入充电任务；进阶层启用充电调度后，P2 需要配合处理充电任务插入。P2 不强制在自身内部完全解决 AMR 之间的轨迹冲突。若把冲突约束也完全加入 P2，本质上就变成 P2 + P3 的联合调度模型，复杂度会明显上升。

## 2. P2 的输入与输出

### 2.1 输入

P2 应主要使用以下数据：

```text
data/raw/tasks.csv
data/raw/amrs.csv
data/processed/p1/<algorithm>/path_cost.csv
```

可选使用：

```text
data/processed/p1/<algorithm>/path_trajectory_samples.csv
data/raw/floor_obstacles.csv
```

其中：

- `tasks.csv` 给出任务取货点、送货点、服务时间、最早开始时间、最晚完成时间、优先级；
- `amrs.csv` 给出 AMR 初始位置、电量、速度等属性；基础层 P2 必须使用 `speed` 和 `battery`，进阶层启用充电调度后还需要处理充电任务；
- `path_cost.csv` 给出 P1 计算好的候选路径及其距离、通行时间、综合成本，`<algorithm>` 可选 `basic_astar/vg/avg/davg`，带 `planning_status` 列标记规划失败的 OD 对；
- `path_trajectory_samples.csv` 可用于 P2 做粗略轨迹冲突风险估计，但不是基础版必需输入。

### 2.2 输出

P2 应继续输出当前项目已有接口：

```text
data/processed/p2/assignment_result.csv
data/processed/p2/amr_sequence_summary.csv
```

其中 `assignment_result.csv` 至少应包含：

```text
amr_id
task_id
sequence_order
pickup
delivery
transition_path_uid
loaded_path_uid
estimated_start_time
estimated_finish_time
estimated_delay
transition_status
loaded_path_status
assignment_method
```

这能保证 P3 继续读取 P2 的结果，不需要大幅改接口。

## 3. 硬约束：必须满足的指标

硬约束是指如果不满足，方案就不应被认为是可行的。结合当前代码和工程实际，建议 P2 至少满足以下硬约束。

### 3.1 每个任务必须被分配

基础版默认所有静态任务都必须完成：

```text
每个 task_id 必须且只能分配给一台 AMR
```

等价于整数规划中的：

```text
sum_k x[k,j] = 1
```

暂不建议在基础 P2 中允许任务拒绝。如果后续要允许低优先级任务不执行，可以引入 `unassigned_task_penalty` 或未完成变量，但这属于扩展功能。

### 3.2 同一 AMR 的任务必须形成线性序列

每台 AMR 被分到的任务应形成一个明确的执行序列：

```text
AMR1: T01 -> T06 -> T10
AMR2: T02 -> T08
```

不应出现同一任务有多个前驱或多个后继，也不应出现任务环。

### 3.3 任务载货路径必须存在

对每个任务，必须存在：

```text
pickup -> delivery
```

的可行路径。

如果某个任务本身的取货点到送货点没有路径，那么该任务无法被正常执行。P2 应将其判为不可行或给出明确错误，而不是静默生成结果。

### 3.4 任务间衔接路径必须存在

如果某台 AMR 的任务顺序为：

```text
T_i -> T_j
```

则必须存在：

```text
delivery_i -> pickup_j
```

的空驶衔接路径。

对于每台 AMR 的第一个任务，也必须存在：

```text
amr_init_node -> pickup_j
```

的空驶路径。

在边权图版本（main 分支）中，出库点是单向死端，baseline 会出现 `OUT2 -> P4`、`OUT1 -> P8` 这类衔接路径缺失。当前二维平面图分支中 AMR 可以从出库点返回主区域，该问题已不存在，但优化版 P2 仍应把"衔接路径必须存在"作为硬约束保留（`planning_status != ok` 的 OD 对仍可能出现缺失）。

### 3.5 最早开始时间不能违反

任务不能早于 `earliest_start` 开始：

```text
start_time[j] >= earliest_start[j]
```

如果 AMR 提前到达取货点，可以等待；不能提前开始任务。

### 3.6 同一 AMR 同一时刻只能执行一个任务

同一台 AMR 的任务应按序串行执行：

```text
start_time[next] >= finish_time[current] + transition_time[current,next]
```

这属于任务排序与时间衔接的基本可行性要求。

### 3.7 AMR 速度必须参与时间估算

P2 估算时间时，必须按命题规定使用 AMR 的 `speed`：

```text
empty_time = base_travel_time / speed
loaded_time = base_travel_time / (speed * 0.90)
```

### 3.8 电量阈值必须参与可行性检查

基础层 P2 必须按命题规定计算空驶、载货和服务耗电，并保证 AMR 任务序列中任意时刻剩余电量不低于安全阈值。基础层不允许插入充电任务，若某个任务插入方案导致电量低于阈值，该方案不可行。进阶层启用充电调度后，P2 需要配合处理充电任务插入。

## 4. 软指标：尽量优化的目标

软指标不是绝对不能违反，而是越小越好。正式 P2 可以把多个软指标组合成一个目标函数。

### 4.1 总路径成本

路径距离、通行时间和综合成本的字段来源与量纲，以 [项目命题规定.md](./项目命题规定.md) 第 9.3 节为准。P2 中的 `cost` 默认指 `path_cost.csv` 的 `total_cost`，是抽象综合成本，不是距离。

包括两部分：

```text
空驶成本：AMR 当前点 -> 任务取货点
载货成本：任务取货点 -> 任务送货点
```

总路径成本可写为：

```text
total_path_cost = sum(transition_cost + loaded_cost)
```

这是 P2 最基础的优化目标。

### 4.2 总完工时间 Cmax

`Cmax` 表示所有任务完成时间中的最大值：

```text
Cmax = max(finish_time[j])
```

工程含义是：这一批任务最晚什么时候全部做完。仓储调度中通常希望 `Cmax` 越小越好。

### 4.3 延期相关指标

如果任务完成时间超过 `latest_finish`，产生延期：

```text
delay[j] = max(0, finish_time[j] - latest_finish[j])
late[j] = 1 if delay[j] > 0 else 0
```

`latest_finish` 建议在当前项目中作为软约束处理：可以晚完成，但要付出惩罚。这样比直接判不可行更稳健。

延期按命题规定同时考虑四项：

```text
priority_late_count = sum(priority[j] * late[j])
late_count = sum(late[j])
priority_delay = sum(priority[j] * delay[j])
total_delay = sum(delay[j])
```

含义分别是：高优先级任务是否延期、有多少任务延期、高优先级任务延期得有多久、总共晚了多久。评价顺序固定为：先减少高优先级延期任务，再减少延期任务数量，再减少高优先级延期时长，最后减少总延期时间。

### 4.4 AMR 负载均衡

负载可以有多种定义：

```text
任务数量负载：每台 AMR 分到的任务数
时间负载：每台 AMR 的预计工作时间
成本负载：每台 AMR 的路径成本 + 服务时间
```

当前项目更建议使用时间负载：

```text
load[k] = AMR k 的最后完成时间，或该 AMR 的总服务时间 + 总行驶时间
```

负载均衡惩罚可以定义为：

```text
load_balance_penalty = sum(abs(load[k] - average_load))
```

或者更简单：

```text
load_balance_penalty = max(load[k]) - min(load[k])
```

### 4.5 等待时间

如果 AMR 提前到达任务取货点，需要等待到 `earliest_start`：

```text
waiting[j] = max(0, earliest_start[j] - arrival_pickup_time[j])
```

等待时间过多说明任务释放节奏或分配顺序不合理。可将总等待作为软目标：

```text
total_waiting = sum(waiting[j])
```

### 4.6 粗略冲突风险

严格的轨迹冲突应由 P3 处理。但 P2 可以做轻量级风险规避，例如：

- 对 `dynamic_cost > 0`（穿越动态风险区域）的路径增加额外惩罚；
- 对 `turn_count` 多的路径增加惩罚（转弯多意味着在密集区域穿行）；
- 对同一时间附近经过相近区域的任务序列增加冲突风险分。

这一项建议作为增强版目标，而不是基础硬约束。

## 5. 目标函数

P2 的正式评价口径服从 [项目命题规定.md](./项目命题规定.md) 第 10 节，采用分层字典序目标与层内加权目标相结合的多目标规划准则。

服务质量层：

```text
F1 = (priority_late_count, late_count)
```

时间效率层：

```text
F2 = 30.0 * priority_delay
   + 20.0 * total_delay
   + 5.0  * Cmax
```

运行成本层：

```text
F3 = 2.0  * empty_cost
   + 10.0 * load_balance_penalty
   + 1.0  * total_energy_used
```

P2 静态调度目标为：

```text
min lex (F1, F2, F3)
```

在算法实现中，若需要比较两个候选插入方案，必须按以下顺序比较：

```text
1. priority_late_count；
2. late_count；
3. F2；
4. F3。
```

## 6. 可选算法路线

### 6.1 当前 baseline：贪心分配

当前代码采用的是 baseline 贪心方法：

```text
按 earliest_start、priority、latest_finish 排序任务；
逐个任务选择当前 score 最小的 AMR；
score = 当前 AMR 负载 + 初始点到取货点成本 + 载货成本 + 缺失路径惩罚。
```

优点：

- 实现简单；
- 能快速生成 P3 所需接口；
- 适合做对比基线。

主要不足：

- 分配阶段没有真实考虑 AMR 上一个任务结束后的位置；
- 没有把任务顺序作为优化变量；
- 没有严格避免任务间衔接路径缺失；
- 没有显式优化 Cmax、延期和负载均衡；
- 没有考虑粗略冲突风险。

### 6.2 保底改进：最近插入启发式

推荐作为当前项目 P2 的第一版优化算法。

核心思想：

```text
逐个插入任务，但不是只看 AMR 初始点；
而是尝试把任务插入每台 AMR 当前任务序列的所有可能位置；
计算插入后的总目标函数增加量；
选择增量最小的位置。
```

步骤：

1. 按 `earliest_start`、`priority`、`latest_finish` 对任务排序；
2. 初始时每台 AMR 任务序列为空；
3. 对当前任务 `j`，尝试插入每台 AMR 的每个位置；
4. 对每个候选插入方案，重新计算该 AMR 的局部时间表；
5. 若出现衔接路径缺失，则该插入方案不可行；
6. 计算目标函数增量；
7. 选择增量最小的插入位置；
8. 所有任务插入完成后，输出任务分配与顺序。

优点：

- 实现难度适中；
- 能显著改善当前 baseline 的衔接路径缺失问题；
- 自然支持任务排序；
- 可以纳入延期、Cmax、负载均衡等软目标；
- 不需要引入复杂求解器。

### 6.3 中级改进：局部搜索

在最近插入法得到初始解后，可以继续做局部搜索：

```text
同一 AMR 内交换两个任务顺序；
不同 AMR 之间移动一个任务；
不同 AMR 之间交换两个任务；
```

每次操作后重新计算目标函数。如果目标变好且硬约束满足，则接受修改。

可用策略：

- first improvement：找到一个更好的方案就立即接受；
- best improvement：遍历所有邻域，选择提升最大的方案；
- 限制最大迭代次数，避免运行时间过长。

### 6.4 进阶方案：0-1 整数规划任务指派

文档中提到的整数规划可用于任务指派：

```text
x[k,j] = 1 表示任务 j 分配给 AMR k
```

基础约束：

```text
sum_k x[k,j] = 1
```

目标可包括：

```text
分配成本
任务数量负载均衡
高优先级任务惩罚
```

但单纯 `x[k,j]` 只能解决“谁做哪个任务”，不能完整解决“任务顺序”。如果要同时优化顺序，需要加入：

```text
u[k,i,j] = 1 表示 AMR k 在任务 i 后执行任务 j
```

这会变成类似多车辆路径问题或带时间窗车辆路径问题，模型复杂度明显提升。

### 6.5 进阶方案：任务指派 + 排序联合 MILP

联合模型可包含：

```text
x[k,j]：任务指派
u[k,i,j]：任务前后顺序
S[j]：任务开始时间
C[j]：任务完成时间
D[j]：任务延期
Cmax：系统完工时间
```

核心约束：

```text
每个任务必须分配给一台 AMR
每台 AMR 的任务形成一条序列
若 i 在 j 前，则 S[j] >= C[i] + transition_time[i,j]
C[j] >= S[j] + service_time[j] + loaded_time[j]
S[j] >= earliest_start[j]
D[j] >= C[j] - latest_finish[j]
Cmax >= C[j]
```

该方案更符合运筹学建模表达，但实现和调试成本较高。适合小规模精确验证，不建议一开始直接用于完整算例。

### 6.6 不建议 P2 直接承担的内容

以下内容建议保留给 P3 或 P4：

- 精确的二维轨迹 footprint 冲突检测；
- 轨迹冲突的等待避让策略；
- 换路修复策略；
- 动态区域封锁后的滚动重排。

P2 可以输出更好的初始方案，但不必承诺最终无冲突。

## 7. 当前项目最推荐的 P2 实现路线

结合当前代码规模、接口和完成难度，推荐按三步升级。

### 第一步：修复 baseline 的关键缺陷

必须解决：

```text
分配和排序时考虑 AMR 当前真实位置；
避免任务间 transition path missing；
把空驶时间/成本纳入负载；
输出字段保持兼容。
```

这一步完成后，任何 `planning_status != ok` 或 P1 未生成的 OD 对都不应再被静默选入任务链（在边权图分支上这一步对应消除 `OUT2 -> P4`、`OUT1 -> P8` 类缺失）。

### 第二步：实现最近插入启发式

将任务逐个插入 AMR 序列的最佳位置，而不是简单追加或按时间窗排序。

插入评价函数建议包含：

```text
路径成本增量
完成时间增量
总延期增量
延期任务数变化
优先级延期惩罚
负载均衡变化
```

### 第三步：加入局部搜索

在插入法结果基础上继续优化：

```text
同车任务交换
跨车任务移动
跨车任务交换
```

局部搜索能进一步降低 Cmax、延期任务数、总延期和负载不均衡。

## 8. P2 结果的验收指标

为了判断 P2 是否比 baseline 更好，建议至少比较以下指标：

```text
scheduled_task_count       成功形成可行任务链的任务数
missing_transition_count   任务间衔接路径缺失数量
missing_loaded_path_count  任务载货路径缺失数量
estimated_cmax             粗略最大完成时间
estimated_priority_late_count 粗略优先级加权延期任务数
estimated_total_delay      粗略总延期
estimated_late_count       粗略延期任务数
estimated_priority_delay   粗略优先级加权延期
total_path_cost            总路径成本
empty_travel_cost          空驶成本
loaded_travel_cost         载货成本
load_balance_range         最大负载 - 最小负载
```

P2 改进版至少应做到：

```text
missing_transition_count = 0
missing_loaded_path_count = 0
estimated_priority_late_count 不高于 baseline
estimated_total_delay 不高于 baseline
estimated_late_count 不高于 baseline
estimated_cmax 不高于或接近 baseline
负载均衡优于 baseline
```

如果某些指标互相冲突，例如 Cmax 降低但路径成本上升，应在报告中解释权重取舍。

## 9. 和 P3 的接口关系

P2 应向 P3 提供：

```text
每台 AMR 的任务顺序
每个任务的空驶路径 path_uid
每个任务的载货路径 path_uid
粗略开始/完成时间
```

P3 在此基础上继续完成：

```text
按实际出发时间把 path_uid 对应的轨迹样本展开为绝对时空轨迹
检测 AMR 之间的轨迹 footprint 冲突
必要时通过等待、换路、调序等方式修复
```

因此，P2 的目标是生成高质量初始排程，而不是替代 P3。

## 10. 推荐报告表述

可以在报告中这样描述 P2：

```text
P2 模块在候选路径成本矩阵基础上，完成多 AMR 任务分配与任务排序。
模型将“每个任务必须由一台 AMR 执行、任务间必须存在可行衔接路径、任务不能早于最早开始时间执行”作为硬约束；
将系统最大完成时间、总路径成本、总延期、延期任务数量、优先级加权延期和 AMR 负载均衡作为软优化目标。
在求解方法上，先以贪心策略作为 baseline，再采用最近插入与局部搜索方法改进任务序列质量。
P2 输出的任务序列和路径选择结果交由 P3 展开二维时空轨迹并检测 footprint 冲突。
```

## 11. PDF 中与 P2 相关的解答建议

本节整理两个 PDF 中与 P2 相关的解答建议。这些内容不是题目硬性要求，正式题干仍以 [项目命题规定.md](./项目命题规定.md) 为准。

### 11.1 建议对比的方法

PDF 建议在“任务分配与调度效果”实验中比较三类方法：

```text
最近任务贪心：
每个任务分给当前估计成本最低或距离最近的 AMR。

普通指派：
建立基于成本矩阵的 0-1 指派模型，只决定任务给哪台 AMR，弱化或暂不考虑通道冲突。

协同调度：
综合考虑任务分配、任务顺序、候选路径、时间窗和后续冲突消解结果。
```

这三类方法适合作为由浅到深的实验对照。当前 baseline 可作为“最近任务贪心”的代表；改进版 P2 可对应“普通指派”或“协同调度”的任务分配与排序部分。

### 11.2 建议比较指标

P2 相关实验建议至少记录：

```text
Cmax                         系统最大完成时间
late_count                   延期任务数量
priority_late_count          高优先级延期任务指标
total_delay                  总延期时间
priority_delay               优先级加权延期
empty_cost                   空驶综合成本
total_path_cost              总路径综合成本
total_distance               总行驶距离
load_balance_penalty         AMR 负载不均衡
missing_transition_count     任务间衔接路径缺失数量
solve_time                   求解时间
```

如果实验接入 P3 的冲突检测结果，还应补充：

```text
conflict_count               冲突数量
average_waiting_time         平均等待时间
total_waiting_time           等待时间
unresolved_conflict_count    未解决冲突数量
```

### 11.3 建议做的敏感性实验

PDF 中与 P2 关系最紧密的是两类敏感性实验：

```text
AMR 数量敏感性：
改变 AMR 数量，观察 Cmax、延期、空驶成本、负载均衡和冲突数量的变化。

任务密度敏感性：
改变任务数量或任务释放密度，观察延期率、求解时间、负载均衡和冲突修复压力的变化。

目标权重敏感性：
若 P2 实现了加权目标函数，可改变延期、空驶、负载均衡和能耗权重，观察任务分配与排序结果是否发生明显变化。
```

其中 AMR 数量和任务密度是 P2 最直接相关的两类敏感性实验；目标权重敏感性属于可选展示，更适合在报告中和 P5 的综合分析一起呈现。实验重点不是简单证明“改进算法一定更好”，而是找到适用边界：任务少、空间宽松时，贪心策略可能已经接近可用；任务密度升高或空间资源紧张时，协同调度才会明显降低延期和冲突。

### 11.4 建议的 P2 完成层次

PDF 对 P2 的解答路线可以整理为：

```text
保底解法：
最近任务贪心；
基于成本矩阵的简单指派；
输出每台 AMR 的任务列表。

进阶解法：
0-1 整数规划任务指派；
加入负载均衡；
加入任务优先级；
加入任务顺序优化；
在初始解基础上做插入启发式或局部搜索。
```

其中保底解法用于跑通完整系统和提供对比基线；进阶解法用于体现运筹学建模深度。

### 11.5 建议展示的结果表

P2 部分可展示以下表格：

```text
任务分配表：
task_id, pickup, delivery, assigned_amr

AMR 任务序列表：
amr_id, task_sequence, estimated_finish_time, estimated_delay

方法对比表：
method, Cmax, late_count, total_delay, total_distance, empty_cost, load_balance_penalty, solve_time
```

若与 P3 联合展示，可在方法对比表中增加：

```text
conflict_count, average_waiting_time, total_waiting_time, unresolved_conflict_count
```

## 12. 一句话总结

P2 最合理的目标不是“直接解决全部多 AMR 无冲突调度”，而是在 P1 给出的路径成本基础上，尽可能生成一个任务完整、衔接可行、延期较小、负载较均衡的任务分配与排序方案，为 P3 的冲突检测和调度修复提供高质量初始解。
