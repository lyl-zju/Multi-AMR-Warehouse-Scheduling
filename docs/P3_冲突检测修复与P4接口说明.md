# P3 冲突检测、修复与 P4 接口说明

本文档重点说明：P3 做了什么、输出格式有什么变化、P4 应该读取哪些文件。

## 1. P3 的位置和目标

P1 负责生成仓库平面图上的候选路径，P2 负责 AMR 分配、任务排序和路径选择。P3 不重新做 P2 的全局任务分配，而是在 P2 给出的静态计划基础上，进一步生成可执行的时空轨迹，并检测、修复多机器人运行冲突。

P3 的核心输入来自：

```text
data/processed/p2/assignment_result.csv
data/processed/p1/mixed/path_cost.csv
data/processed/p1/mixed/path_trajectory_samples.csv
```

P3 的核心输出给 P4 使用：

```text
data/processed/p3/schedule_result.csv
data/processed/p3/trajectory_schedule.csv
```

其中 `schedule_result.csv` 是修复后的任务时间表，`trajectory_schedule.csv` 是修复后的 0.1 秒粒度时空轨迹表。

## 2. P3 做了什么

P3 当前完成了以下工作：

1. 读取 P2 的任务分配、任务顺序和路径选择。
2. 读取 P1 mixed 路径库中的几何路径和候选路径。
3. 按 P2 的实际行驶时间，把 P1 路径几何展开成 0.1 秒粒度的时空轨迹。
4. 检测机器人之间的空间 footprint 冲突。
5. 检测 `P*`、`SORT*`、`OUT*` 点位容量冲突。
6. 比较多种修复策略。
7. 选择目标函数最优的修复结果。
8. 输出 P4 可继续读取的 schedule 和 trajectory。

P3 的冲突检测包括两类。

空间冲突：

```text
distance < footprint_radius_1 + footprint_radius_2 + safety_margin
```

当前参数：

```text
footprint_radius = 0.25
safety_margin = 0.10
clearance threshold = 0.60
TIME_TOLERANCE = 0.25
TRAJECTORY_SAMPLE_STEP = 0.10
```

节点容量冲突：

```text
P*, SORT*, OUT* 同一时刻最多只能有一台 AMR 占用或工作。
```

P3 还会显式建模静止占用，包括：

```text
wait_at_pickup
service_at_pickup
repair_wait_at_node
mid_path_wait_transition
mid_path_wait_loaded
```

机器人完成全部任务后，轨迹结束；结束后的机器人不再参与冲突检测。GIF 中完成的机器人会淡化显示。

## 3. P3 修复策略

P3 当前比较三种修复模式：

```text
wait
wait_reroute
wait_reroute_resequence
```

三种模式含义如下。

### 3.1 wait

只通过等待修复冲突。等待动作可以是：

```text
wait_before_task      任务开始前等待
mid_path_wait         路径中间暂停
```

### 3.2 wait_reroute

在等待基础上，允许换路。

换路约束：

```text
只能从 P1 mixed 的同 OD 候选路径中选择。
不能生成 P1 之外的新路径。
不能改变任务分配和任务顺序。
```

### 3.3 wait_reroute_resequence

在等待和换路基础上，允许同一 AMR 内部局部换序。

换序约束：

```text
只能交换同一 AMR 内的相邻任务。
不能把任务从一台 AMR 移到另一台 AMR。
换序后重新计算 transition_path_uid 和相关时间。
loaded_path_uid 仍对应该任务的 pickup -> delivery。
```

注意：当前代码已经支持 `mid_path_wait`、换路和同车相邻换序。当前这组 P1/P2 数据下，最终最优解没有实际使用换路或换序，而是主要通过冲突点前的路径中途暂停让行消解冲突。

## 4. 目标函数和选择规则

P3 先按剩余冲突数做最高优先级选择：

```text
min remaining_conflicts
```

若剩余冲突数相同，再比较目标函数：

```text
J = 100 * total_delay
  + 5 * Cmax
  + total_wait_added
  + 2 * reroute_count
  + 20 * resequence_count
  + 20 * initial_wait_added
```

当前 `repair_summary.csv` 记录的选择规则为：

```text
min remaining_conflicts, then 100*delay+5*Cmax+wait_added+2*reroute_count+20*resequence_count+20*initial_wait_added
```

当前运行结果：

```text
mode,selected,initial_conflicts,remaining_conflicts,total_delay,Cmax,total_wait_added,reroute_count,resequence_count,initial_wait_added,objective
wait,0,21,0,0.0,46.59697,16.0,0,0,0.0,248.98485
wait_reroute,0,21,0,0.0,46.59697,16.0,0,0,0.0,248.98485
wait_reroute_resequence,1,21,0,0.0,46.59697,16.0,0,0,0.0,248.98485
```

解释：三种模式都能修到 0 冲突，指标相同。当前通过 tie-break 选中 `wait_reroute_resequence`。实际：

```text
reroute_count = 0
resequence_count = 0
initial_wait_added = 0
```

也就是说，代码能力上支持换路和换序，但这组数据中没有实际触发更优换路或换序；冲突主要由 `mid_path_wait_loaded` 这类路径中途暂停让行动作解决。

典型修复日志如下：

```text
iteration 1: AMR2/T02 loaded mid_path_wait +20s, remaining conflicts 16
iteration 2: AMR3/T01 loaded mid_path_wait +5s,  remaining conflicts 7
iteration 3: AMR4/T08 loaded mid_path_wait +8s,  remaining conflicts 4
iteration 4: AMR2/T02 loaded mid_path_wait +5s,  remaining conflicts 2
iteration 5: AMR2/T02 loaded mid_path_wait +5s,  remaining conflicts 0
```

等待压缩后，最终统计为 `total_wait_added = 16.0`，`total_delay = 0.0`。

## 5. 输出文件说明

P3 输出目录：

```text
data/processed/p3/
```

主要文件：

```text
schedule_result.csv
trajectory_schedule.csv
conflict_log.csv
repair_summary.csv
```

### 5.1 schedule_result.csv

这是 P3 最终选中方案的修复后任务时间表。

重要格式约定：

```text
表头严格沿用 P2 的 data/processed/p2/assignment_result.csv。
不额外新增列。
```

这样做是为了保证 P3 不额外扩展任务级表头。新版 P4 会通过 `normalize_p3_schedule()` 将 P3 的 `estimated_*` 字段转为 P4 内部使用的 `start_time`、`finish_time`、`delay`、`waiting_time` 和 `schedule_status`。

虽然表头沿用 P2，但里面的值已经由 P3 更新，包括：

```text
estimated_arrival_pickup
estimated_start_time
estimated_finish_time
estimated_delay
estimated_waiting
transition_path_uid
transition_path_id
transition_travel_time
transition_distance
transition_cost
loaded_path_uid
loaded_path_id
loaded_travel_time
loaded_distance
loaded_cost
energy_used
battery_after
assignment_method
notes
```

`assignment_method` 会追加 P3 后缀，例如：

```text
m3_regret_insertion_ls+mixed+p3_wait_reroute_resequence
```

`notes` 中记录该行任务是否被 P3 加等待、换路或换序影响。

当前最终方案中，AMR2 不再开局长时间等待。其首个任务 T02 正常执行到载货段后，在路径中途暂停让行：

```text
T02 estimated_start_time = 3.589
T02 estimated_finish_time = 18.162333
T02 estimated_delay = 0.0
T02 estimated_waiting = 4.0
```

P4 如果只需要任务级调度结果，应优先读取：

```text
data/processed/p3/schedule_result.csv
```

不要再直接读取 P2 的 `assignment_result.csv` 作为最终执行计划，因为 P2 没有处理时空冲突。

### 5.2 trajectory_schedule.csv

这是 P3 最重要的 P4 接口文件之一。它是修复后的时空轨迹表，只包含 P3 最终实际采用的路径和等待段。

字段如下：

```text
amr_id
任务所属 AMR。

task_id
当前轨迹点属于哪个任务。

sequence_order
该任务在该 AMR 内的执行顺序。若 P3 发生同车换序，此字段是修复后的顺序。

segment_type
轨迹段类型，例如 transition、loaded、service_at_pickup、wait_at_pickup、repair_wait_at_node、mid_path_wait_transition、mid_path_wait_loaded。

path_uid
该轨迹点对应的路径 ID。中途等待会使用 midwait::<原path_uid>。

sample_index
该段内采样点序号。

absolute_time
全局绝对时间，单位秒。P4 做动态调度或仿真时应主要使用这个字段。

offset_time
相对该段起点的时间偏移。

x, y
平面坐标。

theta
朝向。

speed
速度。等待或服务段为 0。

footprint_radius
机器人 footprint 半径，当前为 0.25。
```

当前最终轨迹中会出现 `mid_path_wait_loaded`。它表示 AMR 已经沿 P1 路径行驶到冲突点前某个采样位置，然后原地等待对方通过，之后继续沿原路径前进。该动作不是倒退，也不是离开原路径避让。

P4 如果需要做动态仿真、滚动调度、实时冲突检查或动画，应优先读取：

```text
data/processed/p3/trajectory_schedule.csv
```

P4 不需要再把 P1 全部候选路径重新展开。P3 已经只保留最终方案真正用到的时空轨迹。

### 5.3 conflict_log.csv

这是 P3 修复过程日志，不是最终轨迹表，也不是 P4 必须读取的执行输入。

字段：

```text
mode
iteration
conflict_id
conflict_time
conflict_type
before_conflicts
action
target_amr
target_task
target_sequence_order
segment_type
old_path_uid
new_path_uid
wait_added
after_conflicts
objective
```

用途：

```text
调试 P3 修复过程
写报告时解释 P3 做了哪些动作
比较 wait / wait_reroute / wait_reroute_resequence 的修复过程
```

P4 一般不需要依赖此文件。

### 5.4 repair_summary.csv

这是三种修复模式的结果摘要。

字段：

```text
mode
selected
initial_conflicts
remaining_conflicts
total_delay
Cmax
total_wait_added
reroute_count
resequence_count
initial_wait_added
objective
selection_rule
```

P4 如果需要知道当前 P3 最终采用哪种模式，可以读取：

```text
selected == 1
```

当前选中：

```text
wait_reroute_resequence
```

但 P4 的执行数据仍应以 `schedule_result.csv` 和 `trajectory_schedule.csv` 为准。

## 7. P4 应该怎么接 P3

P4 推荐读取顺序：

```text
1. data/processed/p3/repair_summary.csv
   查看 selected == 1，确认 P3 最终采用的修复模式。

2. data/processed/p3/schedule_result.csv
   读取最终任务级时间表，保持 P2 表头格式。

3. data/processed/p3/trajectory_schedule.csv
   读取最终 0.1 秒粒度时空轨迹，用于动态仿真、滚动调度或二次冲突检测。
```

新版 P4 可以直接读取当前 P3 输出。若接入的是旧版 P4，则至少需要做字段映射：

```text
start_time      <- estimated_start_time
finish_time     <- estimated_finish_time
delay           <- estimated_delay
waiting_time    <- estimated_waiting
schedule_status <- transition_status == ok 且 loaded_path_status == ok
path_uid        <- loaded_path_uid
```

P4 需要把 `mid_path_wait_loaded` 和 `mid_path_wait_transition` 当作普通静止轨迹段处理：它们有 `absolute_time`、`x`、`y`、`footprint_radius`，且 `speed = 0`。因此 P4 做动态区域封锁、滚动调度或二次冲突检测时，应继续基于 `trajectory_schedule.csv` 的采样点判断。

P4 不建议直接使用：

```text
data/processed/p2/assignment_result.csv
```

原因：P2 输出没有处理多机器人时空冲突。P3 的 `schedule_result.csv` 才是冲突修复后的最终 schedule。

P4 一般也不需要直接使用：

```text
data/processed/p1/mixed/path_trajectory_samples.csv
```

原因：P3 已经在 `trajectory_schedule.csv` 中输出了最终实际使用的时空轨迹。

## 8. 与第一版 P3 相比的主要变化

相比第一版，当前第二版 P3 的关键变化如下：

```text
1. 使用第二版 P1 的 0.30 障碍膨胀路径，满足 0.25 机器人半径约束。
2. 严格读取 P2 mixed 任务安排和路径选择。
3. 轨迹按 0.1 秒重新采样。
4. 检测 moving footprint 冲突。
5. 检测 P/SORT/OUT 节点容量冲突。
6. 显式建模等待、服务、中途暂停等静止占用。
7. 输出 P2 表头兼容的 schedule_result.csv。
8. 输出 P4 友好的 trajectory_schedule.csv，而不是照搬 P1 路径表。
9. 增加 repair_summary.csv，比较多种 P3 修复模式。
10. 增加 wait_reroute_resequence 模式，支持同车相邻任务换序。
11. 增强 mid_path_wait 候选生成，在冲突点前 0.8-4.0 秒范围内尝试中途暂停让行。
12. 增加零冲突后的等待压缩，只保留保持 0 冲突所需的等待量。
```

## 10. 注意事项

1. `conflict_log.csv` 是修复过程日志，不代表最终仍有冲突。最终是否有冲突看 `repair_summary.csv` 的 `remaining_conflicts`。
2. 当前 `initial_conflicts = 21` 是事件级去重后的冲突数。早期版本曾报告 248，是原始 0.1 秒采样点级冲突数。
3. 当前最优结果虽然选中 `wait_reroute_resequence`，但实际 `reroute_count = 0`、`resequence_count = 0`。
4. 当前 P3 使用的是提前停车/中途暂停让行，不是倒退让行。轨迹中的 `mid_path_wait_loaded` 表示在原路径上停车，等待后继续前进。
5. AMR2 不再开局长时间等待；其等待主要发生在载货路径中途。P4 如果按轨迹采样点判断动态事件，应将该等待段视为 AMR 对该位置的静止占用。
6. 新版 P4 可直接读取当前 P3 输出；旧版 P4 需要按第 7 节做字段映射。
